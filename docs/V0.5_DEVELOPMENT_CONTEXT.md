# MediPrompt v0.5 Development Context — Gap Score and Semantic Coverage

Status: build brief for v0.5. Consolidates the v0.5 scope into one executable contract, the same
way `V0.4_DEVELOPMENT_CONTEXT.md` did for content coverage.
Base: `develop` at PR #18 (v0.4 content coverage, merged to main via PR #19; v0.4 live on Pages).
Branch: `feature/v0.5-gap-score-and-semantic`.

This brief is the single source of truth for v0.5 implementation. If code and this brief disagree,
the brief wins until it is amended.

## 1. What v0.5 is

v0.5 closes the practice loop and sharpens the coverage match — both on-device:

- **The loop closes (Gap Score).** After the review screen, the learner can re-attempt the *same*
  topic. The second attempt is scored the same way as the first. **Gap Score** is the change in
  weighted coverage fraction between attempt 2 and attempt 1 (`Δ = w2 − w1`). It is shown as the
  single most important number on the second review, with a plain-language direction
  (improved / flat / regressed). This is the headline novel metric: it makes "did this attempt help
  you close the gap?" legible.
- **Semantic cosine coverage (optional enhancer).** The v0.4 lexical matcher is retained as the
  guaranteed baseline. An optional `all-MiniLM-L6-v2` embedding engine (transformers.js, lazy
  on-device, same-origin ORT runtime already vendored for Whisper) computes cosine similarity
  between the transcript and each concept's accepted phrases, hitting a concept when similarity
  clears a calibrated threshold. When the embedding model is unavailable (offline first run, low
  memory, declined), coverage falls back to the lexical engine transparently. The score shape
  (`CoverageReport`) is unchanged; only the matcher is upgraded.

The v0.4 review screen (transcript → coverage → prescription → delivery) is unchanged for attempt 1.
v0.5 adds the re-attempt path on top of it and an enhancer behind it.

## 2. What is explicitly excluded

- **Spaced resurfacing / exam-countdown queue:** v0.7. v0.5 holds attempt history in-session only
  (no persistent weak-topic queue yet).
- **Viva Round follow-ups (Recall→Explain→Apply→Differentiate→Defend):** v0.6. The v0.5 re-attempt
  is a same-topic second attempt, not a follow-up question ladder.
- **Persistent history across sessions / backend storage:** still out. Attempt history lives in
  the in-memory session (and the existing IndexedDB settings store is not extended to attempts).
- **A "correctness" grade or emotion/confidence inference:** unchanged L1 non-goals. Gap Score is a
  coverage delta, not a correctness delta.
- **Calibrated rejection / observability-aware thresholds for the semantic engine:** the cosine
  threshold is a single documented constant in v0.5; calibrated rejection is a v0.8+ research item.
- Accounts, backend, server storage: still out.

## 3. Gap Score and the second attempt

### 3.1 State machine

The `REVIEW` state gains the concept of an attempt index. After attempt 1's review:

- `REVIEW` (attempt 1) → `START_SECOND_ATTEMPT` event → `TOPIC_READY` re-using the same
  `TopicSnapshot` and a fresh `AttemptDraft` whose `attemptIndex: 2`.
- The second attempt runs the full v0.3/v0.4 path (speak → record → transcribe → approve → score).
- `REVIEW` (attempt 2) carries both `coverage` (attempt 2) and `priorCoverage` (attempt 1), plus
  `gapScore: number` and `gapDirection: "IMPROVED" | "FLAT" | "REGRESSED"`.

No new recording/transcription machinery — the existing pipeline is reused. The reducer stays pure;
`gapScore` is computed in the orchestrator at attempt-2 approval (it has both reports) and threaded
through the event, mirroring how `coverage` and `textMetrics` are computed outside the reducer.

### 3.2 Gap Score definition

- `gapScore = coverage2.weightedFraction − coverage1.weightedFraction` (a value in `[−1, 1]`).
- `gapDirection`: `IMPROVED` if `gapScore > 0`, `REGRESSED` if `< 0`, `FLAT` if `=== 0`.
- Display: the number as a signed percentage ("+18%") with the direction word and one
  prescription line that references the *still*-missed concept with the highest weight
  (re-using `prescribe` on attempt 2's report), or the FULL line when attempt 2 covers everything.

### 3.3 Attempt history

A small in-session `AttemptHistory` (array of `{ attemptIndex, coverage, transcript text }`) is
kept in orchestrator state and surfaced to the review screen for traceability. It is not persisted.
A third+ attempt is allowed in v0.5 (the loop can repeat), but Gap Score is always
attempt-current − attempt-previous.

## 4. Semantic cosine engine

`src/scoring/semanticCoverage.ts` + `src/scoring/embed.worker.ts` + `src/scoring/embeddingClient.ts`.

- `all-MiniLM-L6-v2` (`Xenova/all-MiniLM-L6-v2`, ~22 MB, Apache-2.0), pinned revision. Loaded lazily
  on explicit activation, same pattern as the Whisper transcription worker: progress, cancel,
  stale-drop by `attemptId`, same-origin ORT runtime (already vendored under `public/models/ort/`
  for Whisper — reused, not duplicated).
- Embed the approved transcript once; embed each concept's accepted phrases once per rubric (cache
  per pack+variant). Cosine similarity per phrase; a concept hits when its best phrase similarity
  ≥ `SEMANTIC_HIT_THRESHOLD` (documented constant, default 0.75, adjustable in settings later).
- The output is a `CoverageReport` (same shape as lexical). The orchestrator chooses semantic when
  available and activated, else lexical. This is feature-gated exactly like audio
  (`speechFeedbackAvailable` capability + explicit opt-in); in jsdom/CI the lexical path runs, so
  tests stay deterministic and no model downloads in CI.
- Fallback is mandatory: any load/low-memory/timeout/cancel/decline path falls back to the lexical
  `scoreCoverage` for the same transcript+concepts. The learner is never blocked by the model.

### 4.1 What the lexical engine retains

`src/scoring/coverage.ts` is unchanged in behavior. It remains the contract for CI, offline-first
run, and the no-model path. The semantic engine wraps it, never replaces it.

## 5. UI changes

- `AttemptReview` gains an optional `priorCoverage` + `gapScore` block above the attempt-2 coverage:
  a "Gap Score" line (`aria-live="polite"`) showing the signed delta and direction, plus a one-line
  reading. Attempt 1 renders without it.
- A "Try again on this topic" action on the review screen starts the second attempt (re-uses the
  same `TopicSnapshot`).
- An "Attempts" traceability list (attempt index + coverage %) appears behind a `<details>`.
- The semantic-vs-lexical provenance is **not** shown to the learner in v0.5 (it is an
  implementation detail; the score is the score). A debug flag may surface it for the beta tester.

## 7. Budget and build gate

- The semantic engine reuses the already-vendored ORT wasm runtime (`public/models/ort/`); no new
  wasm. The embedding model weights download lazily at runtime (like Whisper) and are SW-cached.
- `validate-build.mjs`: the transformers.js worker graph for embeddings is already part of the
  bundled worker budget (shared library). Watch the shell budget (v0.4 is at ~1.52 MiB of the
  1.5 MiB cap — embedding client code is small, but verify after build). Entry-JS budget unaffected
  (lazy worker).
- CSP unchanged (`wasm-unsafe-eval` scoped; no `unsafe-inline`/`eval`).

## 8. Exit gate (v0.4 + these additions)

- No raw audio or transcript leaves the browser. (unchanged)
- No score before transcript approval. (unchanged)
- Coverage is never a correctness grade. (unchanged)
- Gap Score is a coverage delta, never a "you got smarter" claim. (v0.5 addition)
- Semantic coverage must fall back to lexical on any model failure; the learner is never blocked
  or shown a failed model state. (v0.5 addition)
- The not-verifiable fallback still applies when a rubric has no scorable concepts, for either
  engine. (unchanged)
